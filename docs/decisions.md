# Architecture Decision Log

One entry per significant decision. Newest at the bottom.

Format:
- **Date** | **Decision** | **Options considered** | **Why** | **What I'd change at scale**

---

- **2026-10-27** | Hybrid architecture: scraping outside Databricks, lakehouse on Databricks, frontend outside | All on Databricks; all outside; hybrid | Free Edition blocks most outbound internet and Apps stop after 24h; hybrid mirrors enterprise landing-zone pattern | Run ingestion on managed compute with a service principal; host the frontend as a Databricks App on a paid workspace
- **2026-10-28** | Claude Code as primary dev tool, context in version-controlled CLAUDE.md plus docs/ | Cursor; Claude Code; both | Terminal-first fits scraping, CLI and Git work; context is reproducible and reviewable | Same, plus shared team conventions in CLAUDE.md
- **2026-10-28**: Rejected scraping UFCStats after the UFC terms of use were found to prohibit automated access and database building; fighter stats to come from a licensed MMA API instead. At scale, negotiate a commercial data licence.
- **2026-10-30** | UFCalendar ingestion: incremental rules | Re-fetch recent events every run; refresh on a fixed interval; webhooks | Every-run refresh would spend ~14 requests per recent event per run and exhaust the free quota. Chosen: fetch by numeric id (slugs can 308-redirect); events from the last 14 days re-fetched at most every 72 hours; round stats re-fetched only when a bout's result changes; fighters re-fetched after they fight again; ETags sent on re-fetch. Estimated steady state for UFC on a free key: about 190 requests/month of 1,000 | Use UFCalendar webhooks (deliveries do not count against quota) from a hosted endpoint instead of polling
- **2026-10-30** | Run the UFCalendar ingestion as Databricks serverless jobs, deployed with an Asset Bundle; laptop kept as fallback | Laptop; GitHub Actions; cloud VM; Databricks job | An egress test from serverless reached api.ufcalendar.com, removing the reason for running API ingestion outside Databricks (the 2026-10-27 decision still applies to scraping websites). The job runs as me so no unattended token is needed, the key lives in a secret scope, schedule and logs are in the Jobs UI, and job plus code deploy together from Git. A run lock stops laptop and job writing the manifest at once; the backfill job refuses to run below a 30,000/month plan and runs in 1-hour chunks to stay inside fair usage | Run as a service principal from CI with separate dev and prod targets, alert on failure, and keep egress allowlisted explicitly
- **2026-11-22** | Hobby plan for the backfill: UFC first, plan-dependent job settings as bundle variables and job parameters | Keep hard-coded free-plan values and override per run; separate jobs per plan; variables and job parameters | The 4 November override dropped the plan guard (see learning log). Orgs are processed in the order given, so the backfill finishes UFC history before PFL, OKTAGON and RIZIN. The incremental job widens to all four orgs (10 latest events each, budget 600, 55/min); this overlaps with the backfill rather than adding to it. The backfill gets a daily 14:00 schedule that deploys PAUSED (unpaused later the same day at the owner's request, see `docs/status.md`). The Hobby quota period runs 22 November to 22 December 2026. **Open decision (by about 19 December):** renew Hobby or downgrade. Remaining work is about 18,500 requests (about 7 runs of 3,000), so one period should be enough; renew only if the backfill is unfinished. On downgrade, set `incremental_orgs=ufc`, `incremental_rpm=8`, `incremental_budget=100` and pause the backfill schedule before the plan changes | One job per org with its own quota pool, and an automatic check of `/v1/usage` that adapts rpm and budget to the plan |
- **2026-11-22** | Finish the backfill in one long run instead of daily 1-hour chunks | Daily 3,000-request chunks; larger chunks; one run of about 16,000 requests | The manifest is saved every 25 requests, so a stopped run loses almost nothing and the next run resumes. The incremental job is not needed until later, so the main risk of a long run (a fair-usage block that stops all jobs for a day or more) is acceptable. Job timeout raised from 2 h to 6 h; the default budget stays 3,000 for scheduled runs | With a paid workspace, no fair-usage risk: run per org in parallel tasks, each with its own budget |
- **2026-11-22** | Bronze layer for the UFCalendar landing files: processed-files log, MERGE on natural key, raw JSON payload, separate bundle | Auto Loader with checkpoint; processed-files log plus MERGE; append-only bronze with dedupe in silver. Payload as VARIANT, as parsed columns, or as a JSON string. Bronze job in the root bundle or in its own | A log table gives exact control of run size (`--max-events` subset, `--max-files` cap) and keeps selection logic pure and unit-testable; Auto Loader cannot cap a run cleanly. MERGE on key with latest `fetched_at` wins (ties: file modification time, then path) keeps bronze one row per key, so silver reads a clean table; the log keeps every file version for audit. A raw JSON string survives API schema drift (a fingerprint of key paths makes drift visible) and lets silver be rebuilt from bronze alone. Files are read only after a 10 minute quiet window, empty files are skipped, and truncated or non-200 files are logged as rejected and never reach bronze, so a backfill that is still writing cannot corrupt the load. A separate bundle (`bronze/databricks.yml`, name `mma-bronze`) means a deploy cannot overwrite the ingestion jobs while the backfill runs. Subset tests go to `mma.bronze_dev`; the full load is a parameter change (`schema=bronze`, `max_events=0`) | Auto Loader with file events and a Lakeflow pipeline for bronze to silver; keep every fetch (append-only) if history of changes matters; merge the bronze job into the main bundle once the backfill is done; VARIANT for the payload where the runtime allows it
