# Architecture Decision Log

One entry per significant decision. Newest at the bottom.

Format:
- **Date** | **Decision** | **Options considered** | **Why** | **What I'd change at scale**

---

- **2026-10-27** | Hybrid architecture: scraping outside Databricks, lakehouse on Databricks, frontend outside | All on Databricks; all outside; hybrid | Free Edition blocks most outbound internet and Apps stop after 24h; hybrid mirrors enterprise landing-zone pattern | Run ingestion on managed compute with a service principal; host the frontend as a Databricks App on a paid workspace
- **2026-10-28** | Claude Code as primary dev tool, context in version-controlled CLAUDE.md plus docs/ | Cursor; Claude Code; both | Terminal-first fits scraping, CLI and Git work; context is reproducible and reviewable | Same, plus shared team conventions in CLAUDE.md
- **2026-10-28**: Rejected scraping UFCStats after the UFC terms of use were found to prohibit automated access and database building; fighter stats to come from a licensed MMA API instead. At scale, negotiate a commercial data licence.
- **2026-10-30** | UFCalendar ingestion: incremental rules | Re-fetch recent events every run; refresh on a fixed interval; webhooks | Every-run refresh would spend ~14 requests per recent event per run and exhaust the free quota. Chosen: fetch by numeric id (slugs can 308-redirect); events from the last 14 days re-fetched at most every 72 hours; round stats re-fetched only when a bout's result changes; fighters re-fetched after they fight again; ETags sent on re-fetch. Estimated steady state for UFC on a free key: about 190 requests/month of 1,000 | Use UFCalendar webhooks (deliveries do not count against quota) from a hosted endpoint instead of polling
- **2026-10-30** | Run the UFCalendar ingestion as Databricks serverless jobs, deployed with an Asset Bundle; laptop kept as fallback | Laptop; GitHub Actions; cloud VM; Databricks job | An egress test from serverless reached api.ufcalendar.com, removing the reason for running API ingestion outside Databricks (the 2026-10-27 decision still applies to scraping websites). The job runs as me so no unattended token is needed, the key lives in a secret scope, schedule and logs are in the Jobs UI, and job plus code deploy together from Git. A run lock stops laptop and job writing the manifest at once; the backfill job refuses to run below a 30,000/month plan and runs in 1-hour chunks to stay inside fair usage | Run as a service principal from CI with separate dev and prod targets, alert on failure, and keep egress allowlisted explicitly
- **2026-11-22** | Hobby plan for the backfill: UFC first, plan-dependent job settings as bundle variables and job parameters | Keep hard-coded free-plan values and override per run; separate jobs per plan; variables and job parameters | The 4 November override dropped the plan guard (see learning log). Orgs are processed in the order given, so the backfill finishes UFC history before PFL, OKTAGON and RIZIN. The incremental job widens to all four orgs (10 latest events each, budget 600, 55/min); this overlaps with the backfill rather than adding to it. The backfill gets a daily 14:00 schedule that deploys PAUSED (unpaused later the same day at the owner's request, see `docs/status.md`). The Hobby quota period runs 22 November to 22 December 2026. **Open decision (by about 19 December):** renew Hobby or downgrade. Remaining work is about 18,500 requests (about 7 runs of 3,000), so one period should be enough; renew only if the backfill is unfinished. On downgrade, set `incremental_orgs=ufc`, `incremental_rpm=8`, `incremental_budget=100` and pause the backfill schedule before the plan changes | One job per org with its own quota pool, and an automatic check of `/v1/usage` that adapts rpm and budget to the plan |
- **2026-11-22** | Finish the backfill in one long run instead of daily 1-hour chunks | Daily 3,000-request chunks; larger chunks; one run of about 16,000 requests | The manifest is saved every 25 requests, so a stopped run loses almost nothing and the next run resumes. The incremental job is not needed until later, so the main risk of a long run (a fair-usage block that stops all jobs for a day or more) is acceptable. Job timeout raised from 2 h to 6 h; the default budget stays 3,000 for scheduled runs | With a paid workspace, no fair-usage risk: run per org in parallel tasks, each with its own budget |
- **2026-11-22** | Bronze layer for the UFCalendar landing files: processed-files log, MERGE on natural key, raw JSON payload, separate bundle | Auto Loader with checkpoint; processed-files log plus MERGE; append-only bronze with dedupe in silver. Payload as VARIANT, as parsed columns, or as a JSON string. Bronze job in the root bundle or in its own | A log table gives exact control of run size (`--max-events` subset, `--max-files` cap) and keeps selection logic pure and unit-testable; Auto Loader cannot cap a run cleanly. MERGE on key with latest `fetched_at` wins (ties: file modification time, then path) keeps bronze one row per key, so silver reads a clean table; the log keeps every file version for audit. A raw JSON string survives API schema drift (a fingerprint of key paths makes drift visible) and lets silver be rebuilt from bronze alone. Files are read only after a 10 minute quiet window, empty files are skipped, and truncated or non-200 files are logged as rejected and never reach bronze, so a backfill that is still writing cannot corrupt the load. A separate bundle (`bronze/databricks.yml`, name `mma-bronze`) means a deploy cannot overwrite the ingestion jobs while the backfill runs. Subset tests go to `mma.bronze_dev`; the full load is a parameter change (`schema=bronze`, `max_events=0`) | Auto Loader with file events and a Lakeflow pipeline for bronze to silver; keep every fetch (append-only) if history of changes matters; merge the bronze job into the main bundle once the backfill is done; VARIANT for the payload where the runtime allows it
- **2026-11-22** | Silver layer for UFCalendar: seven tables, incremental by comparing bronze `ingested_at` with what silver was built from, explicit sponsor list, own bundle | Full rebuild every run; watermark on bronze `ingested_at`; per-key comparison. Strip any lead before the brand, or an explicit sponsor list. One wide table or separate event, bout, fighter, round, odds tables | Silver is small (about 30k bronze rows), but a per-key comparison is exact (a watermark can miss rows when a bronze run overlaps) and cheap, and `--full-refresh` keeps rebuild-from-bronze as a safety net. Children are written first and each parent last, so a crash only means the same rows are redone. A re-fetch reloads the parent's rows (join-based MERGE delete, then upsert), so rows removed upstream do not linger. On 600 real UFC titles a strip-any-lead rule would have wrongly stripped `Noche UFC` and `Road to UFC`, and 24 titles have no org brand at all (`The Ultimate Fighter`, `Tuesday Night Contender Series`, `DWCS Brazil`); the real sponsors were `Crypto.com`, `VeChain` and `Polymarket`, so only listed sponsors are stripped and any other lead is reported for review. Contender Series is flagged from slug or title because they disagree on 2 of 600 events. `fighter_bout` (two rows per fought bout) and `fighter_record` (long, because `records` is keyed by type) are separate tables so Text2SQL gets simple joins. Odds props stay in bronze until a feature needs them. Separate bundle (`silver/`, `mma-silver`) like bronze, to be merged into one two-task pipeline after the full run | Lakeflow declarative pipeline with expectations (enforced quality rules) instead of a hand-written report; Change Data Feed on bronze to drive silver; data contracts on the API payloads
- **2026-11-23** | Back to free-plan job settings once the backfill finished | Keep Hobby settings until 22 December; revert now | History is complete, so Hobby headroom is no longer needed, and reverting early means the jobs are already safe when the plan lapses. Incremental keeps all four orgs at budget 100, 8/min (owner's call: rough estimate 500 to 700 requests/month fits the free 1,000, with little margin; the quota reserve of 100 stops runs before the limit, and a budget stop resumes next run); backfill schedule paused. Fallback if quota runs short: UFC only | Per-org incremental jobs sized from `/v1/usage` |
- **2026-11-23** | Offline backup of the raw landing data in Git, on an orphan branch | Laptop copy with `fs cp -r`; zip on Databricks and commit to `main`; zip and commit to an orphan `data-snapshots` branch | The owner wanted a copy outside Databricks without keeping it locally. One zip (22.5 MB) is far faster to move than 21,000 small files. An orphan branch keeps `main` free of data and can be deleted in one step before the repo goes public, since UFCalendar's terms forbid redistributing the raw dataset | Object storage with versioning and lifecycle rules (e.g. a private S3 or Azure Blob bucket), not Git |
- **2026-11-24** | Phase 1 dashboard: Streamlit on Community Cloud calling the SQL Statement Execution API directly, with navigation in the URL | Databricks App; Streamlit with `databricks-sql-connector`; Streamlit with plain REST calls; a static site built from exports | Databricks Apps need a workspace sign-in and stop every 24 hours, and a static export would redistribute the dataset (UFCalendar terms). Plain REST keeps dependencies to `requests` and `pandas`, keeps auth explicit and testable, and named parameters rule out SQL injection. Page state lives in query parameters (`?view=fighter&id=397&orgs=pfl`), so every page is a shareable link. Tables are static HTML, because Streamlit's interactive tables carry a CSV download button. Warehouse protection: 6-hour result cache, fighter and event lists loaded once and filtered in the session (no query per keystroke), `LIMIT` on every query, 90 s cancel; at most 3 small statements per uncached page view (0.5 to 1.6 s each, measured) | A small API layer between frontend and warehouse with its own cache, or precomputed serving tables (Lakebase or a gold layer) so user traffic never reaches the warehouse; a CDN for static pages
- **2026-11-24** | Dashboard credentials: a dedicated service principal with `SELECT` on `mma.silver` only, OAuth M2M | My personal access token; a PAT issued on behalf of a service principal; a service principal with an OAuth secret; read-only views in a separate app schema | A Free Edition personal token carries my full admin access, so it must not leave my machine. A service principal with `USE CATALOG mma`, `USE SCHEMA mma.silver` and `SELECT ON SCHEMA mma.silver` cannot write anything or read bronze and the raw payloads. OAuth M2M means the deployed secret is exchanged for 1-hour tokens; the workspace exposes the secrets endpoint (checked 2026-11-24). Fallback if Free Edition refuses OAuth secrets: an on-behalf-of PAT with a 90-day expiry. A separate view schema is not worth it yet because silver has no sensitive columns. Remaining risk: a leaked secret allows any read on silver and could use up the fair-usage allowance | Views in a dedicated serving schema, a separate warehouse with query limits for app traffic, secret rotation from a vault, and alerting on unusual query volume
- **2026-11-24** | Dashboard display rules for corners and data caveats | Show corners where reliable; hide corners everywhere; winner and loser only | Winners are listed first everywhere and corner colours are never shown, so one rule works across all orgs and years. Corner order is shown only for undecided bouts where `corner_reliable` is true, with a note that corner A is not a performance stat. Contender Series is its own organisation in the filter. Fight history reads `bout`, not `fighter_bout`, because `fighter_bout` leaves out the one bout with outcome `unknown` and lacks names and method. Three different records are labelled apart: pro MMA and UFC from the source profile, and a record counted from the fights in the app | Same rules, enforced in a shared serving view so the Text2SQL agent (Phase 3) cannot bypass them
- **2026-11-25** | Dashboard principal hardening: request the narrow OAuth scope `sql:read:restricted-query`, and revoke Free Edition's default `CREATE` privileges on `workspace.default` | Keep `all-apis`; per-secret scopes. Leave the default workspace grants; revoke them | The secret created in the UI carries only `sql:read:restricted-query`, which is narrower than `all-apis`, so the app now requests it. Free Edition grants the automatic workspace-users group (which every service principal joins) `CREATE TABLE`, `CREATE VOLUME`, `CREATE FUNCTION`, `CREATE MATERIALIZED VIEW` and `CREATE MODEL` on `workspace.default`, so a leaked dashboard secret could have created objects there. Revoked on 2026-11-25, keeping `USE_SCHEMA`; the owner is the only human user and an admin, so nothing is lost. One secret remains (the second was deleted) | Manage grants as code (Terraform or a bundle), audit effective permissions of every service principal in CI, and keep app principals in a workspace with no default grants
- **2026-11-26** | Continuous integration: GitHub Actions runs the full test suite on every push and pull request, in two jobs (unit tests; bronze and silver on local Spark with Delta) | No CI, tests run by hand; unit tests only; also run against Databricks | Free for this repo, and catches the regressions the hand-run suite already found. No secrets in CI: every test uses fakes or local Spark, so a fork or a leaked log exposes nothing. The Spark job takes about 5 minutes, which is acceptable for a solo repo. Local Spark cannot prove serverless compatibility (learning log, 2026-11-23), so a real run stays in the loop | Require the checks before merging (branch protection), add a short integration job against a dev schema with a read-only principal, and lint and type-check
