# Learning Log

Failures found, how they were diagnosed, how they were fixed. Raw material for interview stories.

Format:
- **Date** | **Component** | **What went wrong** | **How I diagnosed it** | **Fix** | **Before/after (if measurable)**

---

- **2026-10-28** | Landing zone (CLI upload) | `databricks fs cp` failed with "no such directory" | Listed the volume root to confirm it existed, so the missing piece was the `_test` subfolder | Create folders with `databricks fs mkdir` before copying; the scraper's upload step must do the same | Upload failed → succeeded
- **2026-10-30** | Ingestion tests (end-to-end with fake API) | Two-run test failed: expected 4 round fetches and 10 fighter fetches, got 5 and 8 | Recounted the fake cards by hand: one played bout was missed, and fighters who appear on two events were counted twice | Code was correct; fixed the expectation and added a comment explaining the count. Lesson: dedupe across events is exactly what the test should pin down, so derive expected counts from the fixture, not from memory | 18/19 → 19/19 passing
- **2026-11-04** | Scheduled ingestion job (Databricks Free Edition) | The every-third-day run on 4 November never started, and a manual run failed with "Triggering new runs for organization ... is currently disabled temporarily" | Job settings were unchanged and unpaused, and the run history showed nothing since 1 November, so the scheduler had been blocked rather than failing. The Free Edition docs say exceeding fair usage shuts compute down for the day (or month); the exact message is undocumented and remaining quota is not visible | Ran the same chunk from the laptop fallback, which uploads through the Files API and needs no Databricks compute. Lesson: keep a non-compute fallback path, and alert on missed scheduled runs rather than only on failed ones | Job blocked → laptop run fetched 2 new events and resumes on request
- **2026-11-22** | Backfill job (`ufcalendar-backfill`) | The 2026-11-04 run ended SUCCESS after 81.6 min but `listing.ufc.history_complete` stayed `False` | `databricks jobs get-run` showed the run was started with "Run now with different parameters", overriding the task's python_params with free-plan values: `--org=ufc --budget=650 --rpm=8 --quota-reserve=250` and no `--min-plan-quota`. The task output ends with `stopping cleanly: request budget of 650 reached` after 1 list page (650 requests: 1 list, 23 events, 22 odds, 233 rounds, 371 fighters; 255 monthly quota left). A budget or quota stop is a clean stop by design, so the task exits 0, and `history_complete` is only set once a list page says `has_more` is false | Not a code bug: a deliberate free-plan chunk that reported success. Backfill scope and budget are now job parameters, so a manual run changes those two fields and keeps the plan guard. Lesson: overriding python_params replaces the whole list, silently dropping guards; and SUCCESS means "stopped cleanly", not "finished", so check the run summary or the manifest | 36 of about 889 UFC events fetched |
- **2026-11-22** | Scheduled ingestion (`ufcalendar-incremental`) | Owner believed the job had never been scheduled; no runs since 7 November | `databricks jobs list` shows the deployed job (bundle-managed, UI locked) with `0 0 6 */3 * ?` Europe/Amsterdam, `UNPAUSED`. The runs on 31 October, 1 and 7 November have trigger `PERIODIC`, so the scheduler started them; the 30 October runs were `ONE_TIME` (manual). Runs due on 4, 10, 13, 16, 19 and 22 November do not appear at all, which matches the 4 November "triggering new runs ... disabled" block rather than a paused schedule | Follow-up the same day from `system.access.audit` and `system.lakeflow.jobs`: the schedule has been unpaused and unchanged since 30 October (no pause, reset or update after that). Scheduled runs log `runTriggered`; there is none on 4 November or from 8 to 21 November, and no failed trigger attempt either, so the scheduler skipped those slots silently. On 4 November a manual `runNow` at 10:41Z failed with `FEATURE_DISABLED: Triggering new runs for organization ... is currently disabled temporarily`, and one at 14:08Z worked. A manual run on 22 November at 12:01Z also worked. Most likely cause: a Free Edition block on triggering new runs (fair usage), lifted at some point before 22 November. Unconfirmed, because nothing was triggered by hand between 8 and 21 November. The scheduler started the backfill's 13:00Z slot on 22 November (`PERIODIC`), so scheduled triggering works again. Also learnt: `*/3` in the day-of-month field restarts each month (31 Oct then 1 Nov). Lesson: on Free Edition the scheduler can drop runs without any error, so alert on missing runs, not only failed ones | - |
- **2026-11-22** | Bronze load (local Spark and Delta test) | The first end-to-end run loaded 0 files: every file was "not eligible" | Printed the listing: local Spark reports paths as `file:/...` where Databricks reports `dbfs:/Volumes/...`, and my path normaliser only stripped `dbfs:`, so every path failed the landing-layout check and was treated as a stray file | Normalise both schemes in one place (`paths.normalise`). While there, replaced file identity based on timezone-dependent datetimes (collected Spark timestamps use the Python process time zone) with epoch milliseconds, so the same file can never look new on the next run. Lesson: a pure filter that silently drops everything looks like "nothing to do"; the dry-run report prints listed, eligible and to-load counts so that case is visible | 0 files loaded → subset, rerun, full load and re-fetch checks pass (81 tests)
- **2026-11-22** | Bronze load (local Spark and Delta test) | Table creation and MERGE failed locally with a Hive-table warning and then `PARSE_SYNTAX_ERROR` on `spark_catalog.bronze_dev.ufcal_events_list` | Databricks creates Delta tables by default and accepts three-part names in `DeltaTable.forName`; open-source Delta does neither (no provider means a Hive table; `forName` cannot parse a catalog prefix) | `CREATE TABLE ... USING DELTA` explicitly, and SQL `MERGE INTO` over a temp view instead of the Python `DeltaTable` API, which also returns inserted and updated counts. Behaves the same on both. Also corrected my own test: empty files are deliberately skipped (possibly still uploading), not logged as rejected | Local run failed → passes
